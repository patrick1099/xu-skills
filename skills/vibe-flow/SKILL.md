# Vibe Flow：轻量 vibe-coding 主流程

## 核心原则

> 先解决用户的问题，再加刚好够用的流程。

本 skill 只做路由和决策边界，不复制 `vibe-scripts`、`vibe-apps`、`true-north:clarify-needs`、`ai-room` 或项目规范的正文，也不把它们全部串成必经关卡。

## 1. 先判断用户此刻要什么

| 请求 | 动作 |
|---|---|
| 可行性、解释、比较、只读诊断 | 先直接回答；不要擅自转成建项目或改文件 |
| 明确要求构建、修改或修复 | 进入后续流程并完成实现与验证 |
| “可以 / 继续 / 按这个做”且方案已经谈定 | 视为继续实现，不再重复索要批准 |

回答“能不能实现”时，先给结论和关键限制。只有用户要求继续做，或上下文已经明确授权改动，才进入实现。

## 2. 选择工作分支

| 场景 | 路由 |
|---|---|
| 独立 Python 命令行脚本、小工具、自动化 | 加载 `vibe-scripts` |
| 有界面、要打包分发、可能成长为网站的个人 Python 应用 | 加载 `vibe-apps` |
| 公司固件、产品代码、构建系统或已有正式仓库 | 遵守该仓库规范；不要套个人工具技术栈 |
| 不属于以上类型 | 沿用项目现有结构，以最小改动完成 |

前半段澄清方式可以共用；实现结构与验证强度由分支决定。

## 3. 只澄清会改变结果的内容

先检查三件事：

1. 用户真正想得到的可见结果是什么？
2. 用户说的是目标、偏好、建议方案，还是不可违反的硬约束？
3. 哪些缺失信息会让最终行为、数据、成本或范围明显不同？

按复杂度行动：

- **清楚且小、可逆**：直接实现。
- **目标清楚，但涉及数据模型、持久化、主要 UI 流程、模块边界或分发方式**：用三点短设计说明“怎么做 / 为什么 / v1 明确不做什么”，然后继续。纯技术内部选择由 AI 决定，不把库、文件名、类名等反问给用户。
- **结果或约束不清楚**：只问最少的一个具体问题；得到答案后继续。
- **多个目标纠缠、需求持续膨胀、方案与约束严重混淆**：调用 `true-north:clarify-needs` 做厚澄清，收束后回到本流程。

### 用户与 AI 的决策边界

用户决定：

- 目标、可见行为、范围和优先级
- 时间/成本取舍
- 删除、覆盖、迁移、联网、隐私等数据影响
- 会改变产品含义的取舍

AI 决定并说明：

- 库、模块划分、文件名、内部 API
- 普通实现细节和测试工具
- 不改变用户体验的可逆技术选择

## 4. 文档按生命周期生成

- 一次性微工具、单会话能完成：不建需求文档。
- 跨会话、需求仍在演化：维护简短 `docs/NEEDS.md`，记录当前目标、可见行为、硬约束和暂不做。
- 长期维护、以后会按意图重构：调用 `true-north:living-blueprint` 维护自然语言 `docs/BLUEPRINT.md`。

文档是连续工作的记忆，不是开工许可证。不要同时生成一套重复的需求、设计、计划文档。

## 5. 必要时才用 ai-room 做技术决策

只有同时满足以下条件才调用 `ai-room`：

- 需求已经清楚；
- 仍有一个会实质影响架构、可维护性或迁移成本的技术取舍；
- `ai-room` 已在运行，或用户明确想让第二个 AI 参与。

发送一个具体问题和准确文件路径，并写清产物边界。顾问只评审/修订文档，不写代码、测试、构建或部署。

- 收到 `DONE`：主 AI 采用或说明取舍，继续实现；不要无新问题反复送审。
- 收到 `BLOCKED`：仅当阻塞跨越用户决策边界时才询问用户，否则主 AI 自行决断。

不要把 `ai-room` 用于简单任务、每个功能后的例行审查、运行测试/编译/部署、“审查所有东西”或无限评审循环。会话等待与安全压缩规则由 `ai-room` 自己负责，本 skill 不复制。

## 6. 实现时保持轻量

- 先交付最小但完整、可实际使用的一条行为链。
- 保留已有行为、规则和用户写下的意图；不能为了简化或解决冲突而静默删除。
- 不默认要求 TDD、正式计划、工作树、子代理或 Superpowers 全流程；仅在任务风险或用户明确要求时单独采用。
- 遇到会改变行为的冲突时，指出具体冲突并等待用户决定；不要替用户删需求。
- 修改范围与用户授权保持一致，不顺手重构无关代码。

## 7. 以真实使用验证收尾

所有分支都必须做一次与交付形态相符的实际使用检查。除此之外按风险加验证：

### 个人脚本 / 应用

- 数据转换、持久化、迁移、已知回归、边界组合：增加针对性自动化测试。
- UI：启动并走通核心用户路径；只检查语法或接口响应不能代替实际操作。
- 用户要求可分发产物：构建后运行该产物，而不只验证源码模式。
- 一次性微脚本：用代表性输入跑通即可，不为测试形式本身搭框架。

### 公司固件 / 产品代码

遵守仓库规定的编译、静态检查、单元/集成测试、真机或协议验证及文档一致性检查。无法执行的验证要明确说明，不能把“看起来正确”写成“已完成”。

完成时简洁报告：

1. 交付了什么；
2. 实际验证了什么；
3. 哪些高风险项尚未验证。

## 反模式

- 用户问可行性，却先输出一整套流程或开始改文件
- 清楚的小需求仍连续追问、写长方案、反复请求批准
- 把纯技术内部选择甩给用户
- 所有项目强制 brainstorming、TDD、BLUEPRINT 或多代理
- 为“简化”静默删掉原有 rules、行为或需求
- 只跑单测，不跑用户真实入口
- 把第二个 AI 变成永不结束的审查门
