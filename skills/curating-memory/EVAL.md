## RED 裁决记录(用当前 v0.2 SKILL.md,升级前)

逐条依据 v0.2 SKILL.md `## 裁决判据` 表(仅有:提名→skill / 提名→CLAUDE.md / 留 / 删 / 并 / 重分类,共六档,无 hook 档、无日期归一化步骤)实际走一遍:

- **A**("从今往后每次给作者本人的插件发版都同时打 .vsix"):v0.2 判据表「提名→skill」一档的命中信号写的是"正文像步骤、像 checklist、像'每次都这么做'"——这条记忆的措辞("从今往后每次...都...")恰好命中这个信号,会被误判为**提名→skill**。但这其实是一条**自动行为**规则,靠"记住去做"办不到,skill 需要人手动触发才会被读取,发版这个动作本身不会触发 skill 调用,所以提名→skill 保证不了执行。v0.2 六档里没有"hook"这个归宿,**判错**。✗
- **B**(GB2312 编码约定):项目专属静态约定,读上下文即可遵守,命中 v0.2「提名→CLAUDE.md」档的"项目专属的约定/约束,应随那个仓库走"。**判对**。△(记作对,但 v0.2 用词是"提名"而非"归宿路由"框架,只能算基本可用)
- **C**(vsix 六步流程):可复用操作流程,命中 v0.2「提名→skill」档"可复用的操作流程/技法(会反复照着执行的'怎么做')"。**判对**。△(同上,能力覆盖但组织方式旧)
- **D**("上周把模拟器 Phase2 真机验收过了"):v0.2 判据表六档里没有任何一档处理"正文含相对日期"的情况,四步流程里也没有"日期归一化"这一步。走完整个 v0.2 流程,这条记忆最多落到「留」(在进行的项目状态),但"上周"这个相对日期会被原样留在正文里,不会被换算成绝对日期。**判错/漏做**。✗
- **E**("把 protocol-simulator + reconciling 两个 skill 打包成可分发的私有插件"):v0.2 六档里没有"plugin"这一档。这条记忆正文字面提到"两个 skill",最接近 v0.2「提名→skill」档"可复用的操作流程/技法"的信号,会被顺着字面误判为**提名→skill**——但这条记忆讲的其实是把两个已有能力**打包成一个可分发的私有插件**,归宿粒度比单个 skill 大一级,skill 档接不住"打包/分发"这个诉求。v0.2 六档没有 plugin 这一档,**判错**。✗

**RED 结论**:A ✗、B △(可用)、C △(可用)、D ✗、E ✗ —— A、D、E 确认判错/漏做,3/5 有硬伤,证明 v0.2 需要升级到五向归宿路由 + 日期归一化。RED 基线成立。

## GREEN 裁决记录(用升级后的 v0.3 SKILL.md)

逐条依据新版 `## 裁决判据` 表(留 memory / → CLAUDE.md / → skill / → plugin / → hook / 删 / 并 / 重分类 / 归一,九档)重新走一遍:

- **A**("从今往后每次给作者本人的插件发版都同时打 .vsix"):命中新增「→ hook」档的信号——"自动行为('从今往后每次 X 就/之前/之后 Y'),靠'记住'办不到、必须 harness 执行……信号:正文像'每次/每当/以后都/自动'"。这条正文正是"从今往后每次...都..."的措辞,精确命中。**裁决:提名→hook**。✅ 与期望一致。
- **B**(GB2312 编码约定):命中「→ CLAUDE.md」档——"项目专属或全局的静态约定/规则,AI 每次读上下文即可遵守。项目专属→该仓库 CLAUDE.md"。**裁决:提名→CLAUDE.md**。✅ 与期望一致。
- **C**(vsix 六步流程):命中「→ skill」档——"可复用的操作流程/技法('怎么做',会反复照做的步骤/checklist)"。**裁决:提名→skill**。✅ 与期望一致。
- **D**("上周把模拟器 Phase2 真机验收过了"):正文含相对日期"上周",命中新增「归一」档——"用该条 originSessionId 会话日期(或文件 mtime)作锚换算成绝对 YYYY-MM-DD"。按判据表末尾说明"一条记忆可同时命中'归宿'与'归一/精简':先归一,再定归宿"——先把"上周"归一为绝对日期(锚可靠则直接换算,锚不可靠则列入计划表让用户确认,不擅自猜),再判归宿:属于"在进行的项目状态(project)",命中「留 memory」档。**裁决:留 memory + 日期归一化为绝对日期**。✅ 与期望一致。
- **E**("把 protocol-simulator + reconciling 两个 skill 打包成可分发的私有插件"):命中新增「→ plugin」档——"比单个 skill 更大的能力集合,或需分发/多件打包(多 skill+hook+命令)。**提名**并指出并入哪个现有插件或新建"。这条正文正是"把两个已有 skill 打包成一个可分发插件"的措辞,精确命中"多 skill+需分发打包"信号;与「→ skill」档("可复用的操作流程/技法",单一流程的归宿)区分开——E 讨论的是**打包分发多个能力**而非单一可复用步骤,所以落在 plugin 而不是 skill。**裁决:提名→plugin**。✅ 与期望一致,确认 →skill 与 →plugin 边界可判。

**GREEN 结论**:A→hook、B→CLAUDE.md、C→skill、D→留 memory 且日期归一化、E→plugin,**5/5 全部裁决正确**(五向归宿——留memory/CLAUDE.md/skill/plugin/hook——各验证 1 例)。GREEN 成立,v0.3 SKILL.md 升级验收通过,skill 与 plugin 边界经 E 用例验证可判。
